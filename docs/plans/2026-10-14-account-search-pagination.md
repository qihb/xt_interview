# 用户列表搜索与分页 · 落地计划

**目标**：为用户管理页增加用户名、状态、权限级别筛选和分页展示，并通过 `/api/accounts/page` 返回系统通用分页数据模型。
**技术栈 / 约束**：后端沿用 Spring Boot 4.0.6、Spring Data JPA、现有 Account 分层；前端沿用 Vue 3、TypeScript、Element Plus、现有 `request` 封装和 `/api` 代理，并按“业务模块 + 全局通用组件”组织页面代码。
**涉及文件**：
- 后端：新增通用分页响应模型，修改 `AccountRepository`、`AccountService`、`AccountServiceImpl`、`AccountController`。
- 前端：`frontend/web/src/api/index.ts`、用户业务模块目录、用户管理页，以及全局分页组件和组件注册入口。
- 测试：账户服务测试、前端 API/用户管理视图测试（按现有测试结构补充）。
**关键决策**：
- 后端 `page` 从 0 开始，默认 `page=0`、`size=10`；非法或过大的分页参数按接口校验策略处理。
- 分页响应抽象为泛型通用类（例如 `PageResponse<T>`），统一包含 `list`、`totalElements`、`totalPages`、`currentPage`、`pageSize`，账户模块及后续分页模块均复用该模型。
- 查询始终过滤 `deleted = 0`；用户名使用包含匹配，状态和权限级别仅在参数存在时过滤。
- 用户管理按业务菜单建立独立模块目录；状态下拉、权限级别下拉作为用户模块内的业务组件，仅由用户管理模块使用，避免污染全局组件目录。
- 分页器作为全局通用组件，统一封装页码转换、分页事件和视觉样式；业务页面只传入分页数据并监听分页变化。
- 前端分页组件使用 Element Plus 默认 1 基页码，调用接口时转换为 0 基；搜索后重置到第一页。
- 保留现有 `/api/accounts` 全量查询接口，避免影响其他页面或既有调用方。
**执行约定**：本文件仅为计划；由用户指定步骤后再执行，每完成一步勾选并记录验证结果。
